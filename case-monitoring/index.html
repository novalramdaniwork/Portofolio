REPORT-03

Procedure — Alert Pipeline

01
Threshold hit

Prometheus evaluates custom rules every scrape cycle. When a metric crosses its threshold — e.g. CPU > 85% for 5 minutes — the alert transitions to firing.

02
Alertmanager

Receives the firing alert, deduplicates repeats, groups related alerts, and applies inhibition rules — suppressing lower-severity alerts when a higher one is already active.

03
n8n webhook

Alertmanager posts the payload to an n8n webhook. n8n parses the severity label, formats the message, and decides which Telegram channel receives it.

04
Route by severity

Critical → dedicated critical channel. Warning and info → general channel. Different notification formats per severity level.

05
Telegram push

Formatted alert delivered via Bot API — service name, affected host, current value, threshold, timestamp. Real-time push, no polling.

REPORT-04

Routing Plate — Alert Channels

🔴 Critical channel — zero noise

Dedicated channel for alerts that demand immediate action, kept separate so critical issues are never buried under routine notifications: service down/unreachable, MariaDB replication stopped, pod CrashLoopBackOff, disk > 90%, node memory critical.

// SEVERITY: CRITICAL · IMMEDIATE ACTION
🟡 General channel — review in hours

Warnings and informational alerts worth investigating but not urgent enough to page: sustained CPU > 75%, replication-lag warnings, elevated queue depth, non-loop container restarts, disk > 75%. Reviewed as part of daily operations.

// SEVERITY: WARNING · INVESTIGATE

REPORT-07

Parts List — Tech Stack & Decisions

Prometheus

Pull-based metrics with PromQL — the de-facto standard for Kubernetes and container monitoring. Pairs natively with the exporter ecosystem; no custom integrations needed for most services.

// METRICS COLLECTION + STORAGE
Alertmanager

Dedup, grouping, and inhibition prevent alert storms — when a node dies and 20 services report unhealthy, you get one notification instead of 20. Essential for a clean critical channel.

// ALERT DEDUP + GROUPING
n8n

Chosen over custom webhook handlers for visual workflow editing, built-in error handling, and fast iteration — a new alert type or routing rule takes minutes in the UI, not a code deploy.

// ROUTING LOGIC + AUTOMATION
Telegram Bot API

Chosen over email or Slack because it's always on mobile, supports bot interactions (slash commands), and pushes instantly. For a solo DevOps, mobile on-call awareness is critical.

// NOTIFICATION DELIVERY
Grafana

The visual layer over Prometheus for trend analysis and post-incident review — per-service dashboards for quick visual health checks. Complementary to alerting, not a replacement.

// VISUALIZATION + DASHBOARDS
Custom alert rules

Default Prometheus rules fire too often on normal variance. Every rule here was written for this infrastructure's baseline — thresholds calibrated after observing 1–2 weeks of normal behavior.

// CUSTOM THRESHOLDS
REPORT-08

Maintenance Log — Lessons Learned

LL-1
Alert fatigue kills on-call effectivenessThe first version had too many rules firing on normal variance — within a week, real alerts were getting missed. The fix: calibrate thresholds to actual baselines and mercilessly delete rules that fire without action. A quiet critical channel beats comprehensive coverage.
LL-2
Two channels are better than one, but three is too manySeparating critical from general was the highest-impact change. More channels (per-service, per-env) were tempting but created confusion about where to look during incidents. Two channels with clear severity semantics is the right balance.
LL-3
n8n is excellent for alert routing until it goes downIf n8n is down, alerts never reach Telegram. So n8n itself is monitored — a blackbox-exporter uptime check with a fallback direct Alertmanager email route. Monitoring your monitoring sounds ironic; skipping it is a dangerous blind spot.
