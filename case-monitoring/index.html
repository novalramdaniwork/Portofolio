Alert Pipeline Architecture

Metrics flow from exporters into Prometheus. Alertmanager evaluates rules and fires alerts to n8n via webhook. n8n applies routing logic — critical alerts go to a dedicated high-priority Telegram channel, everything else routes to a common channel. The Telegram bot also accepts slash commands for on-demand health checks.

Alert Pipeline · Prometheus → Alertmanager → n8n → Telegram

What's Monitored

Servers
All physical and virtual servers covered via node-exporter. CPU, memory, disk I/O, network throughput, and system load. Thresholds tuned per server based on normal operating baseline.
CPU % RAM % Disk I/O Load avg
Docker Containers
Container-level metrics via cAdvisor. Monitors per-container CPU throttling, memory limits, and restart counts. Alerts fire if a container exits unexpectedly or exceeds resource limits.
CPU throttle Mem limit Restarts Exit status
Kubernetes
Cluster-level monitoring via kube-state-metrics and Prometheus. Tracks pod crash loops, pending pods, node pressure, and deployment rollout failures across all three clusters (dev/staging/prod).
CrashLoopBackOff Pending pods Node pressure
MariaDB Replication
Replication health tracked via mysqld-exporter and custom scripts. Monitors Seconds_Behind_Master, Slave_IO_Running, and Slave_SQL_Running. Alert fires immediately if replication stops or lag exceeds threshold.
Repl lag IO thread SQL thread Queries/s
MongoDB
MongoDB availability and performance via mongodb-exporter. Monitors connection pool utilization, operation latency, and whether the instance is actively accepting connections — critical for services that depend on document storage.
Connections Op latency Up/down
RabbitMQ
RabbitMQ health and queue metrics via the built-in management exporter. Tracks queue depth, consumer count, and message rates. Alerts if queue depth spikes — indicating consumers are down or overwhelmed.
Queue depth Consumers Msg rate Up/down

Alert Pipeline

01
Threshold Hit
Prometheus evaluates custom alert rules on every scrape cycle. When a metric crosses its threshold — e.g. CPU > 85% for 5 minutes — the alert transitions from inactive to firing.
→
02
Alertmanager
Alertmanager receives the firing alert, deduplicates repeated firings, and groups related alerts. Applies inhibition rules — suppressing lower-severity alerts when a higher-severity one is already active.
→
03
n8n Webhook
Alertmanager sends the alert payload to an n8n webhook. n8n parses the severity label, formats the message, and applies routing logic to decide which Telegram channel receives it.
→
04
Route by Severity
n8n checks the severity label: critical alerts route to the dedicated critical channel. Warning and info alerts route to the general channel. Different notification formats per severity level.
→
05
Telegram Push
n8n sends the formatted alert to the appropriate Telegram channel via Bot API. Message includes service name, affected host, current value, threshold, and timestamp. No polling — real-time push.
04

Alert Routing

Critical Channel
Dedicated channel for high-priority alerts that require immediate action. Separate from general alerts to ensure critical issues are never buried under routine notifications. The goal is zero noise in this channel — only things that need immediate attention.
Service down / unreachable
MariaDB replication stopped
Pod CrashLoopBackOff
Disk usage > 90%
Node memory critical
// severity: critical · immediate action required
General Channel
Common channel for warnings and informational alerts. These indicate something worth investigating but not urgent enough to page immediately. Reviewed during working hours as part of daily operations.

On-Demand Health Checks

Passive alerting catches issues automatically, but sometimes you want to check a specific service status on demand — without opening Grafana. Telegram slash commands let me (or anyone with access) query live infrastructure status directly from the Telegram chat.

Each command triggers an n8n workflow that queries Prometheus for current metrics and returns a formatted status summary. The response arrives in seconds — useful during incidents when you need quick situational awareness.

Available Commands
/check_server
CPU, RAM, disk for all servers
/check_db
MariaDB replication status + connections
/check_k8s
Pod status across all clusters
/check_queue
RabbitMQ queue depths + consumer count
/status
Full infrastructure health summary

Tech Stack & Decisions

Prometheus
Pull-based metrics collection with a powerful query language (PromQL). The de-facto standard for Kubernetes and container monitoring. Pairs natively with the exporter ecosystem — no custom integrations needed for most services.
// Metrics Collection + Storage
Alertmanager
Handles alert deduplication, grouping, and inhibition rules. Prevents alert storms — when a node goes down and 20 services report unhealthy, Alertmanager groups them into one notification instead of 20. Essential for keeping the critical channel clean.
// Alert Dedup + Grouping
n8n
Chosen over writing custom webhook handlers because n8n provides visual workflow editing, built-in error handling, and easy iteration on routing logic. Adding a new alert type or routing rule takes minutes in the UI rather than code changes and redeployments.
// Routing Logic + Automation
Telegram Bot API
Telegram was chosen over email or Slack for alert delivery because it's always on mobile, supports bot interactions (slash commands), and push notifications are immediate. As the sole DevOps, on-call awareness via mobile is critical.
// Notification Delivery
Grafana
Grafana provides the visual layer on top of Prometheus for trend analysis and post-incident review. Dashboards per service — servers, Kubernetes, databases — for quick visual health checks during operations. Complementary to alerting, not a replacement.
// Visualization + Dashboards
Custom Alert Rules
Default Prometheus alert rules are too generic — they fire too often on normal variance. Every alert rule was written specifically for this infrastructure's baseline. Thresholds were calibrated after observing normal behavior for 1-2 weeks before enabling alerting.
// Custom Thresholds
08

Lessons Learned

01
Alert fatigue kills on-call effectiveness
The first version of the alerting pipeline had too many rules firing on normal system variance. Within a week, the critical channel was noisy enough that real alerts were being missed. The fix was to spend time calibrating thresholds based on actual baseline behavior and mercilessly deleting rules that fired too often without action. A quiet critical channel is worth more than comprehensive coverage.
02
Two channels are better than one, but three is too many
Separating critical from general was the most impactful change to the alerting setup. Adding more channels (per-service, per-environment) was tempting but created confusion about where to look during an incident. Two channels with clear severity semantics is the right balance — you always know which channel to check first.
03
n8n is excellent for alert routing until it goes down
n8n is a critical piece of the alerting infrastructure — if it's down, alerts don't reach Telegram. I learned to monitor n8n itself (uptime check via blackbox-exporter with a fallback direct Alertmanager email route). The irony of needing to monitor your monitoring tools is real, but ignoring it creates a dangerous blind spot.
