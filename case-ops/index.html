Running inherited infrastructure alone

I took over a multi-cluster Kubernetes setup that someone else had built, as the only DevOps engineer. This is what I run, what I changed, and why I spent the first weeks reading before touching anything.

Role
Sole DevOps engineer, full ownership
Clusters
3 RKE2 clusters on Rancher: dev, staging, prod
Edge
Nginx Proxy Manager with ModSecurity and CrowdSec
Outside Kubernetes
MariaDB, MongoDB, Redis, RabbitMQ, MinIO

What I inherited

The platform was built before I joined. I took over uptime, deployments, incident response and everything that needed improving, on my own.

  • Three RKE2 clusters managed through Rancher, fully isolated: dev for active work, staging for pre-release checks, production for live traffic.
  • One KrakenD gateway per cluster. Every external call goes through Nginx Proxy Manager and then KrakenD before it reaches a service.
  • MariaDB with two masters and one replica, each master serving a different part of the application and both replicating to the same replica.
  • MongoDB, Redis, RabbitMQ and MinIO on dedicated servers outside Kubernetes. None of them heal themselves.

The client is confidential. Names and some details are generalised; the engineering is described as it happened.

Two layers before any service

  • ModSecurity inspects every HTTP request against the OWASP Core Rule Set and blocks SQL injection, XSS and path traversal at the edge.
  • CrowdSec reads the access logs in real time and bans IPs that brute-force, scan or probe, through the proxy’s bouncer.
  • TLS terminates at the proxy with Let’s Encrypt: wildcard certificates for internal subdomains, single-domain ones for public endpoints.
  • KrakenD is the second layer: token validation and per-route rate limits, so unauthenticated requests never reach a service.

What I changed

Alerting that reaches my phone

The setup had dashboards but no automatic alerts. I built Prometheus → Alertmanager → n8n → Telegram with thresholds for clusters, databases, queues and servers, plus slash commands for live checks. The monitoring case study has the details.

Behavioural blocking at the edge

ModSecurity only looks at one request at a time. CrowdSec adds patterns across requests and bans at the proxy automatically.

Nightly off-site backups

Backups used to be manual. A cron job now dumps every database, compresses it and ships it to a remote server over SSH keys, keeps 30 days and reports success or failure to Telegram.

A repeatable certificate process for 50+ domains

Certbot DNS challenges for internal services, the proxy’s manager for public ones, and an HAProxy USR2 reload so certificates swap without downtime.

What I’d tell the next person

You inherit the decisions, not the reasons

Nothing explained why things were set up the way they were. Working that out before changing anything prevented several incidents.

Alone on call, alerting isn’t optional

Nobody can watch dashboards all day. The Telegram pipeline was the most important change I made.

Servers outside Kubernetes are the blind spot

Pods restart themselves; a standalone MariaDB or RabbitMQ doesn’t. Each one needs its own monitoring and a runbook.

Gateway config is the riskiest change

A wrong KrakenD route breaks quietly. Test in dev, run integration tests in staging, then promote. Every time.
