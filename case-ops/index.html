Context & Ownership

Handover context: This infrastructure was built before I joined. I inherited it as the sole DevOps engineer and took full operational ownership — responsible for uptime, deployments, incident response, and continuous improvement. Infrastructure details are intentionally generalized for confidentiality.

Cluster Management
Operate and maintain three separate RKE2 clusters managed through Rancher. Each environment is isolated — dev for active development, staging for pre-release validation, production for live traffic.
RKE2 Rancher dev / staging / prod
API Gateway
Each cluster has its own KrakenD API Gateway instance. All external requests hit Nginx Proxy Manager first, then route through KrakenD before reaching microservices. KrakenD handles routing, rate limiting, and auth validation.
KrakenD NPM API routing
Database Operations
Five standalone database and messaging services running outside Kubernetes. MariaDB with a 2-master + 1-replica setup, MongoDB, Redis, RabbitMQ, and MinIO — all on dedicated servers, all managed solo.
MariaDB MongoDB Redis RabbitMQ MinIO
Security Layer
ModSecurity (WAF) and CrowdSec (IPS) integrated into the Nginx Proxy Manager layer. ModSec filters malicious requests at the HTTP level, CrowdSec provides behavioral threat detection and automatic IP banning.
ModSecurity CrowdSec Nginx Proxy Manager
CI/CD & Deployments
Manage and improve the deployment pipeline across all three environments. Ensure dev and staging pipelines run automatically while production deployments require explicit approval before rollout.
Jenkins GitLab CI ArgoCD

Full monitoring coverage across clusters, standalone servers, and all database services. Custom alert rules with Telegram integration for on-call notifications — all managed and tuned by one person.

Infrastructure Architecture

All external traffic enters through Nginx Proxy Manager with ModSecurity and CrowdSec enforcing security at the edge. Requests then route to the appropriate KrakenD instance per cluster. Standalone database services sit outside Kubernetes and are shared across clusters based on application needs.

What I Operate

01
3 × RKE2 Kubernetes Clusters via Rancher
Dev, staging, and production clusters — each isolated, each managed through Rancher. Responsible for node health, workload scheduling, resource quotas, and rolling deployments. Production cluster runs live traffic; dev and staging are auto-deployed on push.
Kubernetes RKE2 Rancher Helm
02
KrakenD API Gateway — Per Cluster
Three separate KrakenD instances — one per cluster. Every API call from external clients goes through KrakenD before reaching any microservice. Responsible for gateway config management: routes, rate limits, auth validation, and timeout policies. Any config change in one environment must be validated before propagating to production.
KrakenD API routing Rate limiting
03
Nginx Proxy Manager + ModSecurity + CrowdSec
NPM is the single entry point for all external traffic. ModSecurity (WAF) inspects and blocks malicious HTTP requests at the edge. CrowdSec provides behavioral analysis — if a source exhibits attack patterns, it gets banned automatically. Managing security rules and CrowdSec bouncer lists is an active responsibility.
NPM ModSecurity CrowdSec SSL/TLS
04
MariaDB — 2 Masters + 1 Replica
Two MariaDB master nodes with different data sets — Master 1 and Master 2 serve different application domains within the same platform. Both replicate to a single replica node, which acts as a full backup of all data. Responsible for replication health monitoring, backup schedules, user privilege management, and manual failover if needed.
MariaDB Replication Backup automation

Standalone: MongoDB · Redis · RabbitMQ · MinIO
Four additional standalone services — each on dedicated servers outside Kubernetes. MongoDB for document storage, Redis for caching and session management, RabbitMQ for async messaging between services, and MinIO for object storage. All were inherited; responsibility includes monitoring, patching, and ensuring availability.

Security Layer

ModSecurity (WAF)
Web Application Firewall integrated into Nginx Proxy Manager. ModSec inspects every incoming HTTP request against OWASP Core Rule Set — blocking SQL injection, XSS, path traversal, and other common attack patterns before they reach any application layer. Running in detection + blocking mode on production.
// Layer: HTTP Inspection · OWASP CRS
CrowdSec (IPS)
Behavioral Intrusion Prevention System running alongside NPM. CrowdSec analyzes access logs in real time — if a source IP exhibits attack behavior (brute force, scanning, probing), it gets automatically banned via the NPM bouncer. Shares threat intelligence with the CrowdSec community network for proactive blocking.
// Layer: Behavioral Analysis · IP Reputation
SSL/TLS Management
All domains terminate SSL at the NPM layer. Certificates managed via Let's Encrypt with automated renewal. Wildcard certificates for internal subdomains, single-domain certs for public-facing endpoints. Zero-downtime renewal via NPM's built-in cert manager.
// Layer: Transport Security · Certificate Lifecycle
KrakenD Auth Validation
KrakenD acts as the second security layer after NPM. API routes are protected by token validation at the gateway level — unauthenticated requests are rejected before reaching any microservice. Rate limiting per route prevents abuse from authenticated clients.
// Layer: API Security · Auth + Rate Limiting
05

Improvements Made

Inheriting infrastructure doesn't mean accepting the status quo. These are the improvements I implemented after taking ownership — each one reducing operational risk or increasing visibility.

Monitoring
Full Alerting Pipeline
Built end-to-end monitoring with Telegram alerting
The inherited setup had basic monitoring but no automated alerting. I built a complete pipeline: Prometheus → Alertmanager → n8n → Telegram, with custom threshold-based rules for all services — clusters, databases, RabbitMQ, and standalone servers. Critical alerts route to dedicated channels; general alerts go to common. Added /check_server slash commands for on-demand health checks.
Security
CrowdSec Integration
Added behavioral threat detection alongside ModSecurity
ModSecurity was already in place but only inspected request content. I added CrowdSec to complement it with behavioral analysis — detecting patterns across multiple requests from the same source. The NPM bouncer integration means detected threats are blocked at the proxy level without manual intervention.
Database
Backup Automation
Automated nightly backups with remote storage and retention policy
Database backups were previously manual. I wrote Bash scripts that run nightly via cron — dumping all databases, compressing, and shipping to a remote VPS via SSH key authentication. Retention policy automatically purges backups older than 30 days to manage storage. Backup success/failure alerts via Telegram.
Operations
SSL Lifecycle
Systematized certificate renewal across 50+ domains
Managing SSL renewals for 50+ domains manually is error-prone. I documented and standardized the renewal process for both wildcard and single-domain certificates — using Certbot DNS challenge for internal services, NPM's built-in manager for public domains, and HAProxy USR2 reload for zero-downtime cert swaps on load balancer endpoints.
06

Lessons Learned

01
Inheriting infrastructure means inheriting undocumented decisions
Every system has design choices that made sense at the time but aren't documented anywhere. Taking ownership means reverse-engineering why things are set up the way they are before changing anything. I spent the first weeks understanding the architecture before making any modifications — this prevented several potential incidents.
02
Solo DevOps means monitoring is non-negotiable
When you're the only DevOps engineer, you can't watch dashboards 24/7. Building a reliable alerting pipeline isn't optional — it's the only way to catch issues before they become incidents without burning out. The Telegram alerting pipeline I built became the single most important operational improvement I made.
03
Standalone services outside Kubernetes are the operational blind spot
Kubernetes workloads are easy to monitor and restart. Standalone servers running MariaDB, MongoDB, RabbitMQ, and MinIO require more attention — they don't self-heal, and issues require manual intervention. Dedicated monitoring for each service and runbooks for common failure scenarios are essential when you're alone on call.
04
KrakenD config is the most sensitive change in the system
A wrong API gateway config can silently break specific routes without any obvious error. I learned to always test KrakenD config changes in dev first, validate with integration tests in staging, and only then promote to production. The three-cluster setup makes this workflow natural — but it requires discipline to follow every single time.
