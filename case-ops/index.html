REPORT-03

Components — What I Operate

01
3 × RKE2 Kubernetes clusters via Rancher

Dev, staging, production — each isolated, each managed through Rancher. Node health, workload scheduling, resource quotas, rolling deployments. Production runs live traffic; dev and staging auto-deploy on push.

02
KrakenD API Gateway — per cluster

Three separate instances, one per cluster. Every external API call passes through KrakenD before any microservice. Gateway config management — routes, rate limits, auth validation, timeout policies — with changes validated per environment before promotion.

03
Nginx Proxy Manager + ModSecurity + CrowdSec

NPM is the single entry point. ModSecurity inspects and blocks malicious HTTP requests at the edge; CrowdSec adds behavioral analysis with automatic banning. Managing security rules and bouncer lists is an active responsibility.

04
MariaDB — 2 masters + 1 replica

Two master nodes serving different application domains, both replicating to a single replica that acts as full backup. Replication health monitoring, backup schedules, privilege management, manual failover when needed.

05
Standalone: MongoDB · Redis · RabbitMQ · MinIO

Four additional services on dedicated servers outside Kubernetes — document storage, cache/session, async messaging, object storage. All inherited; monitoring, patching, and availability are my responsibility.

REPORT-04

Shield Plate — Security Layer

ModSecurity (WAF)

Integrated into NPM, inspecting every incoming HTTP request against the OWASP Core Rule Set — blocking SQL injection, XSS, path traversal, and other common patterns before they reach any application layer. Detection + blocking mode in production.

// HTTP INSPECTION · OWASP CRS
CrowdSec (IPS)

Behavioral intrusion prevention alongside NPM — analyzes access logs in real time and automatically bans IPs exhibiting attack behavior (brute force, scanning, probing) via the NPM bouncer. Shares threat intel with the CrowdSec community network.

// BEHAVIORAL ANALYSIS · IP REPUTATION
SSL/TLS management

All domains terminate SSL at NPM. Let's Encrypt with automated renewal — wildcard certs for internal subdomains, single-domain certs for public endpoints, zero-downtime renewal via NPM's cert manager.

// TRANSPORT SECURITY · CERT LIFECYCLE
KrakenD auth validation

The second security layer after NPM. API routes protected by token validation at the gateway — unauthenticated requests rejected before reaching any microservice, per-route rate limiting against abuse.

// API SECURITY · AUTH + RATE LIMITING
REPORT-05

Upgrade Log — Improvements Made

Inheriting infrastructure doesn't mean accepting the status quo. Each improvement below reduced operational risk or increased visibility.

Built end-to-end monitoring with Telegram alerting

The inherited setup had basic monitoring but no automated alerting. I built the complete pipeline: Prometheus → Alertmanager → n8n → Telegram, with custom threshold rules for clusters, databases, RabbitMQ, and standalone servers. Critical alerts route to dedicated channels, plus /check_server slash commands for on-demand health checks.

// MONITORING · FULL ALERTING PIPELINE
Added CrowdSec behavioral threat detection

ModSecurity only inspected request content. CrowdSec complements it with behavioral analysis — detecting patterns across multiple requests from one source. The NPM bouncer integration blocks detected threats at the proxy with no manual intervention.

// SECURITY · CROWDSEC INTEGRATION
Automated nightly backups with remote storage

Backups were manual before. Bash scripts now run nightly via cron — dumping all databases, compressing, and shipping to a remote VPS over SSH key auth. A 30-day retention policy purges old backups automatically; success/failure alerts go to Telegram.

// DATABASE · BACKUP AUTOMATION
Systematized SSL renewal across 50+ domains

Manual renewal across 50+ domains is error-prone. I documented and standardized the process — Certbot DNS challenge for internal services, NPM's manager for public domains, and HAProxy USR2 reload for zero-downtime cert swaps on load balancer endpoints.

// OPERATIONS · SSL LIFECYCLE
REPORT-06

Maintenance Log — Lessons Learned

LL-1
Inheriting infrastructure means inheriting undocumented decisionsEvery system has design choices that made sense at the time but aren't written down anywhere. I spent the first weeks reverse-engineering why things were set up the way they were before changing anything — which prevented several potential incidents.
LL-2
Solo DevOps means monitoring is non-negotiableYou can't watch dashboards 24/7 alone. A reliable alerting pipeline is the only way to catch issues before they become incidents without burning out. The Telegram pipeline became the single most important operational improvement I made.
LL-3
Standalone services outside Kubernetes are the operational blind spotKubernetes workloads are easy to monitor and restart. Standalone MariaDB, MongoDB, RabbitMQ, and MinIO don't self-heal — dedicated monitoring per service and runbooks for common failures are essential when you're alone on call.
LL-4
KrakenD config is the most sensitive change in the systemA wrong gateway config can silently break specific routes with no obvious error. Test in dev, validate with integration tests in staging, only then promote to production — every single time.
