Production Kubernetes with RKE2

A government-grade platform has to keep working when a node dies, traffic spikes or a deploy goes wrong. These are the decisions that kept it at 99.9% uptime with zero major incidents.

Control plane
3 nodes, etcd quorum survives one failure
Workers
5, labelled by workload, one fallback
Result
99.9% uptime, zero major incidents
Delivery
Jenkins, Harbor, ArgoCD

What the platform needed

  • No single point of failure. With one control-plane node, losing it makes the whole cluster unmanageable.
  • Workload isolation. Without placement rules, database pods can land next to services and starve them.
  • Room for sudden load. Fixed replica counts either waste capacity or fall over at peak.
  • Safe deploys. Manual production deploys are where mistakes happen.

Control plane and networking

Three control-plane nodes

Three is the minimum for etcd quorum. Any one node can fail and the cluster keeps working, because etcd needs a majority of 2 to elect a leader. If two fail at once the cluster goes read-only but loses no data.

Flannel over Calico

I tested Calico first. Its NetworkPolicy features added work without solving a problem we had, so I switched to Flannel’s simple VXLAN overlay.

Where workloads run

  • Masters 1–3: control plane only (etcd, API server, scheduler, controller manager). No application pods.
  • Workers 1–2: workload: database and services. Database replicas land on different machines.
  • Workers 3–4: workload: services, kept away from heavy database I/O.
  • Worker 5: carries every label. It’s where the autoscaler expands first and where pods go when another node fails.

Every deployment has a Horizontal Pod Autoscaler. That, plus the fallback node, is why traffic spikes never turned into incidents.

From commit to cluster

  1. Jenkins starts automatically on push for dev and staging, and only by hand for production.
  2. It pulls from GitLab, where branches enforce dev → staging → production.
  3. The build gets a semantic version tag, so every image traces back to a commit.
  4. The image is built and pushed to Harbor, which scans it and controls access.
  5. Jenkins updates the image tag in a separate manifest repo.
  6. ArgoCD sees the change and syncs the cluster. Rolling back is a git revert.

What I’d do the same way again

Choose the CNI before production

Switching from Calico to Flannel meant re-networking the cluster. Test the options in staging first.

Plan node labels before the first deploy

Adding labels and nodeSelectors to running workloads needs downtime. Decide the layout up front.

A spare node costs less than an outage

Keeping node 5 as an all-labels buffer felt wasteful. It absorbed every spike.

Keep build and deploy separate

Jenkins builds, Git holds the manifests, ArgoCD deploys. Each step can be audited and rolled back on its own.
