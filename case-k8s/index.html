Production Kubernetes Infrastructure

Multi-environment cluster · High availability · Government-grade

Designing and operating a production Kubernetes cluster for a government-grade platform requires more than just getting pods running. This case study documents the architecture decisions, node strategy, CI/CD pipeline, and operational approach that kept the system at 99.9% uptime with zero major incidents.

The Problem

"A government-grade platform needs infrastructure that doesn't just work — it needs to keep working even when nodes fail, traffic spikes, and deployments go wrong."

The platform required persistent, high-availability infrastructure capable of surviving hardware failures without service interruption. A single control plane would be a single point of failure — unacceptable for production. Worker nodes needed intelligent workload placement to prevent resource contention between services.

Single Point of Failure Risk
A single control plane means the entire cluster becomes unmanageable if that node goes down — unacceptable for production workloads.
Workload Isolation
Without node labeling, database pods could land on the same node as application services — causing resource contention and cascading failures.
Unpredictable Traffic Spikes
Government platforms see sudden load surges. Static replica counts either waste resources or leave the system under-provisioned during peaks.
Deployment Safety
Manual deployments to production are error-prone. A reliable CI/CD pipeline with environment gates was needed to prevent bad code from reaching production.
02

Architecture

Cluster Architecture · High Availability Design
Control Plane Design

Three control plane nodes is the minimum for etcd quorum. With 3 nodes, the cluster tolerates the failure of any 1 node while remaining fully operational. etcd requires a majority (2 of 3) to elect a new leader — if 2 nodes go down simultaneously, the cluster enters a read-only state but doesn't lose data. This is the standard for production Kubernetes.

CNI Choice: Flannel

Flannel was chosen over Calico after testing both in this environment. Calico's additional network policy features added operational complexity without clear benefit for this use case. Flannel provides a simple, reliable overlay network that just works — aligning with the principle of choosing the simplest tool that solves the problem.

Node Labeling Strategy

One of the most important operational decisions was how to organize workloads across worker nodes. Rather than letting the scheduler place pods anywhere, each node was labeled by workload type and workloads were pinned using nodeSelector. This creates predictable, isolated environments that prevent resource contention.

Control Plane
Master Nodes 1–3
Dedicated to Kubernetes control plane components only. etcd, API server, scheduler, and controller manager. No application workloads scheduled here.
node-role: master etcd: true
Worker · DB
Nodes 1 & 2
Database workloads pinned here for predictable I/O and memory. Having two nodes means DB replicas land on different hardware for HA.
workload: database workload: services
Worker · Services
Nodes 3 & 4
Application services and APIs. Isolated from database nodes to prevent heavy DB queries from starving service pods of CPU and memory.
workload: services
Worker · All Labels
Node 5 — Fallback
Carries all workload labels. Acts as overflow when nodes 1–4 are resource-constrained. HPA can expand onto this node before triggering cluster autoscaler.
workload: database workload: services workload: all
HPA
Horizontal Pod Autoscaler
Every deployment is backed by HPA. When CPU or memory thresholds are exceeded, Kubernetes automatically scales replica counts. The fallback node (Node 5) provides immediate capacity before any node provisioning is needed. This is why there were zero major incidents — traffic spikes are absorbed automatically without manual intervention.

Tech Stack & Decisions

Kubernetes RKE2
RKE2 was chosen for its hardened security defaults and simpler operational model compared to vanilla K8s. It ships with a curated set of components that work well together out of the box.
// Orchestration
Rancher
Rancher provides a unified management UI for multiple clusters. It simplifies RBAC, workload management, and monitoring across environments without requiring deep kubectl expertise from every team member.
// Cluster Management
Flannel CNI
Tested Calico first — its NetworkPolicy features added operational overhead without benefit for this use case. Flannel provides reliable VXLAN overlay networking with minimal configuration. Simpler is more reliable in production.
// Container Networking
Jenkins + ArgoCD
Jenkins handles the build pipeline (flexible, battle-tested). ArgoCD handles GitOps-style deployment — cluster state is always driven by Git. Separating build from deploy makes each step auditable and independently rollback-able.
// CI/CD
Harbor Registry
Private container registry with built-in vulnerability scanning. Keeps all images internal — no dependency on external registries in production. Provides access control, image signing, and audit trails.
// Container Registry
HPA
Horizontal Pod Autoscaler scales replica counts based on CPU and memory metrics. The key decision was pairing HPA with a fallback node (Node 5) that has all labels — ensuring scale-out can happen immediately without waiting for new nodes.
// Auto-scaling
07

Lessons Learned

01
Test CNI choices early — switching in production is painful
Starting with Calico and switching to Flannel required re-networking the cluster. Testing CNI options in a staging environment first would have saved significant time. For most production clusters without complex NetworkPolicy requirements, Flannel's simplicity is a feature, not a limitation.
02
Node labeling strategy should be decided before first deployment
Retrofitting node labels and nodeSelectors onto running workloads requires planned downtime. Designing the labeling strategy upfront — and documenting which workloads go where — prevents the "let the scheduler decide" approach that leads to resource contention.
03
A fallback node is cheaper than an incident
Keeping Node 5 with all labels as an overflow buffer felt wasteful at first. In practice, it absorbed every traffic spike and prevented HPA from being unable to scale due to insufficient cluster capacity. The cost of the node is trivial compared to the cost of an outage.
04
Separate the build pipeline from the deploy pipeline
Combining build and deploy in a single pipeline makes rollbacks complicated. The Jenkins (build) → GitLab manifest → ArgoCD (deploy) split means you can roll back a deployment by reverting a Git commit — no need to re-run the build pipeline or understand its internals.
