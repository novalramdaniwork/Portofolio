REPORT-01

Fault Log — The Problem

"A government-grade platform needs infrastructure that doesn't just work — it needs to keep working even when nodes fail, traffic spikes, and deployments go wrong."

The platform required persistent, high-availability infrastructure capable of surviving hardware failures without service interruption.

Single point of failure risk

A single control plane means the entire cluster becomes unmanageable if that node goes down — unacceptable for production workloads.

Workload isolation

Without node labeling, database pods could land on the same node as application services — causing resource contention and cascading failures.

Unpredictable traffic spikes

Government platforms see sudden load surges. Static replica counts either waste resources or leave the system under-provisioned during peaks.

Deployment safety

Manual deployments to production are error-prone. A reliable CI/CD pipeline with environment gates was needed to keep bad code out of production.

Schematic — Cluster Architecture

FIG · CLUSTER ARCHITECTURE · HIGH AVAILABILITY DESIGN
Control plane design

Three control plane nodes is the minimum for etcd quorum. The cluster tolerates the failure of any 1 node while staying fully operational; etcd needs a majority (2 of 3) to elect a leader. If 2 nodes go down simultaneously, the cluster goes read-only but loses no data.

CNI choice: Flannel

Flannel was chosen over Calico after testing both. Calico's NetworkPolicy features added operational complexity without clear benefit here. Flannel provides a simple, reliable overlay network that just works — the simplest tool that solves the problem.

REPORT-03

Procedure — CI/CD Pipeline

The pipeline separates concerns clearly — development and staging auto-deploy on every push, while production requires a manual trigger. This prevents accidental production deployments while keeping lower environments continuously up to date.

01
Trigger

Jenkins job triggered manually (prod) or automatically on push (dev/staging). Environment gates enforced at this stage.

02
Fetch code

Jenkins pulls source from the GitLab repository. Branch strategy enforces dev → staging → production promotion flow.

03
Tag version

Semantic version tag applied to the build. Every image is traceable back to the exact commit that produced it.

04
Build image

Docker image built and tagged. Image scanning planned as the next step — a security layer before pushing to the registry.

05
Push to Harbor

Verified image pushed to the Harbor container registry — image scanning, vulnerability reports, and access control.

06
Update manifest

Jenkins updates the image version in the DevOps GitLab manifest repo. Keeps infrastructure-as-code separate from application code.

07
ArgoCD sync

ArgoCD detects the manifest change and syncs the new version to Kubernetes. GitOps — cluster state is always driven by Git.

PRODUCTION GATE: dev and staging pipelines run automatically on every push. The production pipeline requires explicit manual triggering in Jenkins — full control over when production updates are applied.
REPORT-04

Components — Node Labeling Strategy

Rather than letting the scheduler place pods anywhere, each node was labeled by workload type and workloads pinned with nodeSelector — predictable, isolated environments that prevent resource contention.

Control plane — masters 1–3

Dedicated to Kubernetes control plane components only: etcd, API server, scheduler, controller manager. No application workloads scheduled here.

node-role: masteretcd: true
Worker · DB — nodes 1 & 2

Database workloads pinned here for predictable I/O and memory. Two nodes mean DB replicas land on different hardware for HA.

workload: databaseworkload: services
Worker · Services — nodes 3 & 4

Application services and APIs, isolated from database nodes so heavy DB queries can't starve service pods of CPU and memory.

workload: services
Worker · All labels — node 5 (fallback)

Carries every workload label. Acts as overflow when nodes 1–4 are resource-constrained — HPA expands here before any cluster autoscaling is needed.

workload: databaseworkload: servicesworkload: all
HPA: every deployment is backed by a Horizontal Pod Autoscaler. When CPU or memory thresholds are exceeded, replica counts scale automatically — and node-05 provides immediate capacity. This is why there were zero major incidents: traffic spikes are absorbed without manual intervention.

Parts List — Tech Stack & Decisions

Kubernetes RKE2

Chosen for hardened security defaults and a simpler operational model than vanilla K8s. Ships with a curated set of components that work well together out of the box.

// ORCHESTRATION
Rancher

Unified management UI for multiple clusters — simplifies RBAC, workload management, and monitoring without requiring deep kubectl expertise from every team member.

// CLUSTER MANAGEMENT
Flannel CNI

Tested Calico first — its NetworkPolicy features added overhead without benefit here. Flannel provides reliable VXLAN overlay networking with minimal configuration. Simpler is more reliable in production.

// CONTAINER NETWORKING
Jenkins + ArgoCD

Jenkins handles the build pipeline (flexible, battle-tested); ArgoCD handles GitOps deployment. Separating build from deploy makes each step auditable and independently rollback-able.

// CI/CD
Harbor Registry

Private registry with built-in vulnerability scanning. All images stay internal — no external registry dependency in production. Access control, signing, and audit trails included.

// CONTAINER REGISTRY
HPA + fallback node

Autoscaling on CPU/memory metrics, paired with an all-labels fallback node so scale-out happens immediately — no waiting for new nodes to provision.

REPORT-07

Maintenance Log — Lessons Learned

LL-1
Test CNI choices early — switching in production is painfulStarting with Calico and switching to Flannel required re-networking the cluster. Testing CNI options in staging first would have saved significant time. For most clusters without complex NetworkPolicy requirements, Flannel's simplicity is a feature, not a limitation.
LL-2
Node labeling strategy should be decided before first deploymentRetrofitting node labels and nodeSelectors onto running workloads requires planned downtime. Designing the labeling strategy upfront — and documenting which workloads go where — prevents the "let the scheduler decide" approach that leads to resource contention.
LL-3
A fallback node is cheaper than an incidentKeeping node-05 with all labels as an overflow buffer felt wasteful at first. In practice it absorbed every traffic spike and kept HPA from running out of capacity. The cost of one node is trivial compared to the cost of an outage.
LL-4
Separate the build pipeline from the deploy pipelineCombining build and deploy in a single pipeline makes rollbacks complicated. The Jenkins (build) → GitLab manifest → ArgoCD (deploy) split means rolling back is just reverting a Git commit.
