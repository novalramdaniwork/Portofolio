REPORT-01

Fault Log — The Problem

"A database that can't survive a node failure isn't a production database — it's a scheduled outage waiting for a trigger."

Single node = single point of failure

Any single-node database means one hardware failure or OS issue takes down the platform's entire data layer.

Async replication isn't enough

Standard MySQL/MariaDB replication is asynchronous — a primary can fail after a write but before the replica receives it, losing data. Galera's synchronous wsrep protocol eliminates this.

No load distribution

Single-node setups concentrate all read and write traffic on one server — a bottleneck under load. Multi-master with HAProxy round-robin spreads it evenly.

No reliable backup strategy

Manual backups are inconsistent and easy to forget. Automated nightly backups with remote storage and retention give reliable recovery without operational overhead.

REPORT-02

Schematic — Cluster Architecture

Three Galera nodes form the write cluster — all accept reads and writes with synchronous replication. HAProxy distributes traffic round-robin; Keepalived removes unhealthy nodes from the backend automatically. Two replica nodes sit downstream for read-heavy workloads and as backup sources.

REPORT-04

Procedure — Backup Pipeline

Nightly backups run from the replica nodes — keeping backup load off the production Galera cluster entirely.

01
Cron trigger

Bash script fires nightly on the replica node, scheduled during the lowest-traffic window to minimize I/O impact.

02
mysqldump

Full logical dump from the replica — all databases, stored procedures, triggers. A consistent snapshot without locking any Galera primary node.

03
Compress

gzip typically cuts file size 70–80%. Timestamped filenames for easy identification and retention management.

04
Remote transfer

Shipped to a remote VPS via SCP with SSH key authentication — no passwords, no manual steps. Remote storage means the backup survives local server failure.

05
Retention cleanup

Backups older than 30 days are purged from the remote VPS automatically — bounded storage with a full month of recovery points.

REPORT-06

Parts List — Key Decisions

Galera over standard replication

Standard MariaDB replication is async — there's a window between a write on the primary and it reaching replicas. Galera's synchronous wsrep eliminates that window completely. The consistency guarantee is worth the slight write-latency overhead.

// CONSISTENCY OVER PERFORMANCE
Round-robin vs read/write split

Since all Galera nodes accept writes, round-robin across all three is simpler and equally effective — fewer moving parts, easier to debug, no risk of routing writes to a read-only endpoint.

// SIMPLICITY OVER COMPLEXITY
Replica nodes for backups

Running mysqldump on a Galera node adds I/O load to production. Running it from a replica means zero impact on production query performance — and slight replica lag is irrelevant for nightly backups.

// ISOLATE BACKUP LOAD
Remote VPS for backup storage

Storing backups on the database server defeats the purpose — if the server dies, you lose both. Remote storage over SSH ensures the backup survives exactly the failure you're recovering from.

// BACKUP ISOLATION
Keepalived for auto health

Without it, HAProxy keeps routing to a failed node until someone notices. Keepalived shrinks the blast radius from "degraded until manually fixed" to "degraded for seconds, then auto-healed."

// AUTO RECOVERY
SSH key auth for transfers

Password-based SSH in automated scripts is a security risk — passwords end up in scripts or env vars. Key auth is more secure, doesn't expire, and needs no human in the cron path.

// SECURE AUTOMATION
REPORT-07

Maintenance Log — Lessons Learned

LL-1
Galera quorum is a feature, not a limitationWhen 2 of 3 nodes go down, Galera halts writes. It feels like a failure mode, but it's protecting you — split-brain with conflicting writes is far worse than a brief write pause. The 3-node quorum minimum is a deliberate design choice.
LL-2
Test your backups, not just your backup scriptsA script that runs without errors isn't the same as a backup that restores. Periodically restoring a dump to a test instance and verifying integrity is the only real proof — the pipeline is only as valuable as the last successful restore test.
LL-3
HAProxy health checks need both TCP and SQL probesA Galera node can accept TCP on :3306 while degraded (e.g. during State Snapshot Transfer). A lightweight SQL probe — SELECT 1 or wsrep_ready — ensures HAProxy only routes to nodes actually ready to serve queries.
