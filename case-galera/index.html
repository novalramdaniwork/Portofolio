MariaDB Galera behind HAProxy

One database server was the platform’s single point of failure. I replaced it with a three-node synchronous cluster, health-checked load balancing and nightly off-site backups, and I run it on my own.

Cluster
3 Galera nodes, every node reads and writes
Replicas
2 async, for reads and backups
Backups
Nightly, off-site, 30 days kept
Failover
Automatic, via Keepalived probes

Why one server wasn’t enough

  • One machine, one failure. A disk or OS problem took the whole data layer down.
  • Async replication can lose writes. A primary can fail after committing but before the replica receives it. Galera’s synchronous replication closes that gap.
  • All load on one box. Every read and write competed for the same server.
  • Manual backups. Easy to forget and never tested.

How it fits together

Three equal Galera nodes

Any node accepts reads and writes. A transaction is only acknowledged once all three have it. The third node also feeds the two async replicas.

Quorum on purpose

If two of three nodes go down, the cluster stops accepting writes. That pause is what prevents split-brain and conflicting data.

HAProxy and Keepalived

HAProxy listens on 3306 and spreads connections evenly, about a third each. Keepalived runs TCP and SQL probes and removes or re-adds nodes on its own.

Two replicas

One serves reads that can tolerate a little lag and is the backup source. The other is a hot standby that can be promoted into the cluster.

The backup pipeline

  1. Cron starts the job on a replica during the quietest window, so production nodes do no extra work.
  2. mysqldump takes a full logical dump, including procedures and triggers, without locking a Galera node.
  3. gzip cuts the file by 70–80%, with a timestamp in the name.
  4. SCP ships it to a remote server using SSH keys, so it survives losing the database servers.
  5. Anything older than 30 days is deleted automatically.

What I learned

Quorum is a feature

Halting writes when two nodes are gone feels like failure. Split-brain would be much worse.

Test restores, not just backups

A script that exits cleanly isn’t proof. Restoring a dump to a test instance is.

Probe with SQL, not only TCP

A node can accept connections on 3306 while it’s still syncing. A wsrep_ready check makes sure HAProxy only routes to nodes that can answer.
