MariaDB Galera Cluster + HAProxy

3-node Galera · HAProxy round-robin · Keepalived · Automated backups

Designed and deployed a synchronous multi-master MariaDB cluster to replace a single-point-of-failure database setup. Three Galera nodes with HAProxy load balancing, Keepalived health management, and automated nightly backups with 30-day retention — all built and operated solo.

The Problem

"A database that can't survive a node failure isn't a production database — it's a scheduled outage waiting for a trigger."

The production platform required a database setup that could tolerate node failures without service interruption, distribute read/write load across multiple nodes, and ensure every write is immediately consistent across all nodes — not eventually consistent. Galera's synchronous replication was the right fit.

Single Node = Single Point of Failure
Any single-node database means a hardware failure or OS issue takes down the entire platform's data layer. Unacceptable for production workloads.
Async Replication Isn't Enough
Standard MySQL/MariaDB replication is asynchronous — a primary can fail after a write but before the replica receives it, causing data loss. Galera's synchronous wsrep protocol eliminates this.
No Load Distribution
Single-node setups concentrate all read and write traffic on one server. Under load, this becomes a bottleneck. Multi-master with HAProxy round-robin distributes the load evenly.
No Reliable Backup Strategy
Manual backups are inconsistent and easy to forget. An automated nightly backup with remote storage and retention policy provides reliable recovery options without operational overhead.
02

Cluster Architecture

Three Galera nodes form the write cluster — all nodes accept reads and writes simultaneously with synchronous replication. HAProxy sits in front distributing traffic round-robin. Keepalived monitors node health and removes unhealthy nodes from the HAProxy backend. Two replica nodes sit downstream for read-heavy workloads and as backup targets.

04

HAProxy + Keepalived

HAProxy — Round-Robin
HAProxy listens on port 3306 and distributes every incoming database connection round-robin across all three Galera nodes. Since all Galera nodes accept writes, round-robin is safe — there's no primary/replica distinction at the HAProxy level. This distributes both read and write load evenly across the cluster. Each node handles roughly one-third of all connections under normal operation.
// Load Distribution · Port 3306 · Active-Active
Keepalived — Health Management
Keepalived performs regular health checks against each Galera node — checking both TCP connectivity on port 3306 and a lightweight SQL probe to confirm the node is actually serving queries. If a node fails health checks, Keepalived removes it from the HAProxy backend pool automatically. When the node recovers and passes health checks, it's automatically re-added. No manual intervention required for node failure or recovery.
// Health Checks · Auto Remove + Re-add · TCP + SQL Probe

Backup Pipeline

Nightly automated backups run from the replica nodes — keeping backup load off the production Galera cluster. Dumps are compressed and shipped to a remote VPS via SSH key authentication. A 30-day retention policy automatically purges old backups.

01
Cron Trigger
Bash script triggered nightly via cron on the replica node. Scheduled during lowest-traffic window to minimize any I/O impact on the host.
→
02
mysqldump
Full logical dump via mysqldump from the replica node. Includes all databases, stored procedures, and triggers. Consistent snapshot without locking Galera primary nodes.
→
03
Compress
Dump compressed with gzip — typically reduces file size by 70-80%. Timestamp added to filename for easy identification and retention management.
→
04
Remote Transfer
Compressed backup shipped to remote VPS via SCP with SSH key authentication — no password, no manual intervention. Remote storage ensures backup survives local server failure.
→
05
Retention Cleanup
Script purges backups older than 30 days from the remote VPS. Prevents unbounded storage growth while keeping a full month of recovery points available.

Key Decisions

Galera over Standard Replication
Standard MariaDB replication is async — there's a window between a write on the primary and it reaching replicas. Galera's synchronous wsrep protocol eliminates this window completely. For a production platform, the consistency guarantee is worth the slight write latency overhead.
// Consistency over Performance
Round-Robin vs Read/Write Split
Some setups use HAProxy to split reads to replicas and writes to a primary. Since all Galera nodes accept writes, round-robin across all three is simpler and equally effective. Fewer moving parts, easier to debug, and no concern about routing writes to a read-only endpoint.
// Simplicity over Complexity
Replica Nodes for Backups
Running mysqldump on a Galera node adds I/O load to production. Running it from a replica means the backup process doesn't impact production query performance. The replica is always slightly behind, but for nightly backup purposes the small lag is irrelevant.
// Isolate Backup Load
Remote VPS for Backup Storage
Storing backups on the same server as the database defeats the purpose. If the server dies, you lose both. Remote VPS storage via SSH ensures the backup survives the failure you're trying to recover from.
// Backup Isolation
Keepalived for Auto Health
Without Keepalived, HAProxy would continue routing to a failed Galera node until manually removed. Keepalived makes the removal automatic — reducing the blast radius of a node failure from "cluster degraded until someone notices" to "cluster degraded for seconds then auto-healed."
// Auto Recovery
SSH Key Auth for Backup Transfer
Password-based SSH in automated scripts is a security risk — passwords end up in scripts or environment variables. SSH key authentication is more secure, doesn't expire, and doesn't require human interaction in the cron job execution path.
// Secure Automation
08

Lessons Learned

01
Galera quorum is a feature, not a limitation
When 2 of 3 nodes go down, Galera halts writes. This feels like a failure mode but it's actually protecting you — a split-brain scenario where two nodes accept conflicting writes is far worse than a brief write pause. The 3-node minimum for quorum is a deliberate design choice, not a constraint to work around.
02
Test your backups, not just your backup scripts
A backup script that runs without errors isn't the same as a backup that can actually restore. I learned to periodically restore a backup dump to a test instance and verify data integrity. The backup pipeline is only as valuable as the last successful restore test.
03
HAProxy health checks need both TCP and SQL probes
A Galera node can accept TCP connections on port 3306 but be in a degraded state (e.g. during SST — State Snapshot Transfer). TCP-only health checks won't catch this. A lightweight SQL probe (SELECT 1 or checking wsrep_ready) ensures HAProxy only routes to nodes that are actually ready to serve queries.
