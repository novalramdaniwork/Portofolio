Rebuilding CI/CD for 100+ repositories

Every service was built by a Jenkins job whose script lived on the Jenkins server, from code split between GitHub and GitLab. I replaced that with one versioned pipeline, while the on-premise production kept deploying the old way.

Role
Sole DevOps engineer, design and rollout
Scope
104 repositories audited and synced
Pipeline
Jenkins shared library, GitLab, SWR, ArgoCD
Guardrail
Production needs a version tag and an approval

What was wrong

  • Code in two places. Repositories had moved to GitLab months earlier, but many pipelines still pulled from GitHub, and some GitLab copies were behind.
  • Pipelines outside Git. Each Jenkins job ran a script stored on the server. Old Jenkinsfiles hard-coded git branch: 'master'. No review, no history, hard to reproduce.
  • A second production on the way. The cloud would run next to on-premise for a while, and deploying to one could not be allowed to break the other.
  • Scale. Between 60 and 80 services had to be rebuilt and redeployed. Doing that by hand was not an option.

Audit before touching a pipeline

A script compared the master branch on GitHub and GitLab for every repository through both APIs: 111 on GitHub, 106 on GitLab, 104 in both.

Drifted13Synced from GitHub to GitLab (one on a main branch, synced by hand)

The sync ran on one repository first, which caught two bugs in the sync script before they could touch twenty. A second audit run came back with zero drift.

One pipeline, configured per repository

Each repository now carries two small files. Everything else lives in a shared library that every job loads.

// Jenkinsfile
@Library('platform-pipeline-library@v1.1.8') _
gitopsPipeline()

# cicd/config.yml
project: <project>
application:
  name: <service>
docker:
  dockerfile: Dockerfile
  context: .
  1. Detect version. For production, HEAD must carry a semver tag, or the build stops here.
  2. Build the Docker image.
  3. Push it to the registry (SWR).
  4. Manual approval, production only, with the approver recorded.
  5. Update the manifest repo: clone, bump the image tag, commit and push.
  6. ArgoCD sees the commit and syncs the cluster. Rolling back is a git revert.

The library is versioned and pinned in each Jenkinsfile, so a fix reaches every service, but only when its version is bumped on purpose.

Two productions without collisions

A branch is not an environment

A per-project config maps branches to environments, for example master-cloud to production-cloud. The safety checks look at the environment: anything starting with production needs a tag and an approval. Renaming a branch can’t quietly switch the gate off.

master stays for on-premise

The old jobs hard-code master and still serve live traffic. The cloud builds from a new master-cloud branch, so neither side can break the other. Cleaning up master waits until on-premise is retired.

Rolling it out to dozens of services

  • One pilot end to end: tag, build, registry, approval, manifest commit, ArgoCD sync, pod running. Only then the rest.
  • Scripts for the repetitive parts: create the cloud branch and pipeline files per repository, and clone Jenkins jobs from the pilot through the API.
  • One script bumped the library version in 37 Jenkinsfiles at once.
  • A Groovy script in the Jenkins console moved 38 jobs from an IP-based GitLab address to its domain, run as a dry run first.
  • The new Jenkins runs with Docker Compose on a private cloud VM, reachable only over the VPN.

What I learned

The audit is the cheapest step

Finding 13 drifted repositories before building anything meant no stale code went to production.

Pilot, then scale

One repository surfaced bugs that would otherwise have been in twenty.

Guard environments, not branch names

Branch naming is a team convention and will change. Protection tied to the environment survives that.

A red build can be the right result

Untagged commits stop at version detection on purpose. Dozens of red builds after a bulk change were expected, and nothing reached production.
