Architecture Design Phase — Implementation Planned

On-Premise to Huawei Cloud

Phased migration · Zero data loss · Parallel running strategy

Designed the full architecture and migration plan for moving a government-grade platform from an on-premise Proxmox datacenter to Huawei Cloud. This case study documents the target architecture, phased migration strategy, service mapping, and risk considerations that went into the design.

Current State & Pain Points

On-Premise Hardware Limits
Proxmox-based datacenter has fixed capacity. Scaling requires physical hardware procurement — slow and expensive compared to cloud elasticity.
Manual Database Management
MariaDB master-replica setup requires manual failover. No automated backup management or point-in-time recovery built in.
Limited Observability
Basic monitoring setup. No centralized log management, no cloud-native alerting, and no security scanning across the infrastructure.
No Geographic Redundancy
Single datacenter location. Any regional disruption takes down the entire platform with no automatic failover to a backup site.

Target Architecture

The target architecture separates concerns across Huawei Cloud managed services — compute in CCE, databases in RDS, messaging in DMS, object storage in OBS. A WireGuard VPN tunnel maintains connectivity to on-premise during the phased migration period.

Target Architecture · Huawei Cloud
03

Migration Strategy

The migration is designed as a phased approach — cloud infrastructure runs in parallel with on-premise until the cloud environment is fully stable. Only then does DNS cutover happen, and on-premise is decommissioned. This eliminates big-bang migration risk.

01
Infrastructure Setup
Est. 2–3 weeks
Provision all Huawei Cloud resources. Set up VPC, CCE clusters, managed services (RDS, DMS, DDS, DCS), and establish WireGuard VPN tunnel to on-premise datacenter.
Provision VPC, subnets, security groups
Deploy CCE cluster with KR and INA node pools
Configure RDS instances (MariaDB KR, INA, Temporal)
Set up DMS (RabbitMQ), DDS (MongoDB), DCS (Redis)
Establish WireGuard VPN tunnel for on-prem connectivity
Configure Container Registry (SWR) and update CI/CD pipeline
02
Parallel Running
Est. 3–4 weeks
Deploy all application workloads to cloud while on-premise continues serving production traffic. Validate cloud environment thoroughly — data sync, performance benchmarks, and failover testing.
Deploy all services to CCE — mirror on-prem configuration
Set up database replication from on-prem to RDS (initial sync)
Run parallel traffic testing via internal DNS
Validate observability stack (LTS, CES, HSS, SMN)
Performance and load testing on cloud environment
Document rollback procedure and train team on cloud operations
03
DNS Cutover & Decom
Est. 1–2 weeks
Switch production DNS to cloud. On-premise remains on standby for 1–2 weeks as rollback option. Once stable, decommission on-premise infrastructure and remove VPN tunnel.
Lower DNS TTL 48 hours before cutover
Execute DNS cutover during low-traffic window
Monitor cloud environment intensively for 72 hours post-cutover
Keep on-premise on standby for 1–2 weeks as rollback
Decommission on-premise once cloud is confirmed stable

Risks & Mitigations

Use replication to sync on-prem to RDS before cutover. Validate data consistency before switching traffic. Full backup before any cutover step.

Run parallel load tests during Phase 2. Tune instance sizes and database parameters before cutover.

06

Key Design Decisions

Phased Migration
Big-bang migrations are high-risk. Running cloud parallel to on-prem until stable means the business never goes fully dark during migration. The cost of running both environments temporarily is worth the reduced risk.
// Strategy
WireGuard VPN
WireGuard provides a secure, high-performance tunnel between on-premise and cloud during the migration window. It's simpler to configure than IPSec and has lower latency — critical for database replication sync.
// Connectivity
Managed RDS over Self-Managed
Huawei RDS handles automated backups, point-in-time recovery, and failover. Eliminates the operational burden of managing MariaDB replication manually — which was a pain point in the on-premise setup.
// Database
Dual Region (KR + INA)
Separate CCE node pools and RDS instances for KR and INA regions provides geographic isolation. Each region can operate independently, and ELB routes traffic to the appropriate region based on load.
// Architecture
Huawei Native Observability
LTS for centralized logs, CES for infrastructure metrics, HSS for host security scanning, and SMN for alerting. Using cloud-native tools reduces operational overhead vs running the full observability stack ourselves.
// Observability
SWR Container Registry
Huawei SWR keeps all container images inside the cloud environment — no external registry dependency in production. Jenkins pushes to SWR, ArgoCD pulls from SWR. Simple, secure, and low-latency.
