Moving a government platform from on-premise to Huawei Cloud

A few months ago this page was a design document. Now the migration is running: services are live on the cloud, data is syncing, QA is testing this week, and cutover is the week of 9 November 2026. Below is what was planned, what actually happened, and what’s left.

Role
Sole DevOps engineer, design through cutover
Status
Testing now, cutover week of 9 Nov 2026
Scope
50+ services, 3 source databases, 700+ gateway routes
Main stack
CCE, RDS for MariaDB, Jenkins, ArgoCD, KrakenD

Why move at all

The platform ran on physical servers I inherited: three RKE2 clusters, plus MariaDB, MongoDB, Redis, RabbitMQ and object storage on dedicated machines. It worked, but every limit landed on one person.

  • Capacity was fixed. Scaling meant buying hardware.
  • Databases had no automated backups, point-in-time recovery or failover.
  • There was no second site. One data center problem would take down every environment.
  • With one DevOps engineer, each self-managed server was time taken away from everything else.

The client is confidential. Names, addresses and some figures are generalised; the engineering is described as it happened.

Where it runs now

Requests enter through a cloud load balancer and ingress-nginx, pass through one of two KrakenD gateways, and reach the services. Workflows run on Temporal and sign-in on Keycloak, both inside the cluster. The on-premise side stays warm until cutover is confirmed.

One pipeline for every service

Every service is brought across the same way, so a new one is routine and a broken one is easy to compare with a working one.

  1. The source repo gets a dedicated cloud branch with a Jenkinsfile and pipeline config.
  2. Jenkins builds only from a semver tag and waits for an approval before production.
  3. The image goes to SWR and the pipeline bumps its tag in the manifest repo.
  4. ArgoCD applies the change. Rolling back is a git revert.

Bringing 50+ services across by hand would have taken weeks, so I wrote small tools for the repetitive parts:

  • A repo inspector that reads a service’s code and env files and lists every setting it actually uses.
  • An env translator that maps on-premise hosts, queues and credentials to their cloud equivalents and flags anything it can’t map, like a hard-coded IP.
  • A job generator that clones a known-good Jenkins job for each new service.
  • A gateway checker that compares every backend in the KrakenD config with the services running in the cluster. It found about 30 backends that didn’t exist in the cluster yet.

Where a service had been rewritten from .NET to Go, the Go version replaced it one service at a time. The old one was scaled to zero, not deleted, so switching back is one change.

Keeping data in sync over a bad link

A colleague handled the initial dump and restore into RDS. My job was to close the gap between the dump and the restore, then keep the cloud level with on-premise until cutover.

The link between the two sides drops 30–47% of packets and moves about 50–80 KB/s per connection. Native replication wasn’t a good fit: the target databases have new names, the source accounts have no SUPER privilege, and the connection breaks often. So I wrote a small CDC service in Python.

BinlogReader ─▶ Transformer ─▶ Applier ─▶ CheckpointStore
 (row events)    (rename db)    (idempotent)  (resume point)
                     └─▶ Reconciler  (tables without a primary key)
  • One systemd service per source database, so a slow stream doesn’t hold up the others.
  • Replays are idempotent, so restarting from an earlier position is always safe.
  • Tables without a primary key are excluded from replay and reconciled separately.
  • The overlay network let idle peers fall asleep, so routes stopped working. A pre-start check and a one-minute keepalive timer fixed it.

For tables created after the original restore, replaying days of binlog would have taken about nine hours. Instead I recorded the binlog position, took a snapshot of just those tables, loaded it, and replayed from that position. Row counts and checksums matched on all 13 tables.

What broke along the way

A database down for five days without an alert

A misbehaving pod flooded MongoDB with connections and the log grew to 139 GB. Log rotation with copytruncate needs as much free space as the file, so the disk filled up and mongod stopped. The systemd unit had no restart policy. Fix: Restart=on-failure, hourly rotation so the size cap actually applies, and alarms on disk usage and the process.

A crash loop Kubernetes reported as healthy

A worker still pointed at the on-premise workflow engine. It panicked every ten seconds, but a wrapper inside the container restarted the process, so the pod showed zero restarts. I found it by error volume in the logs, not pod status, and pointed it at the in-cluster Temporal.

Two kinds of gateway 500

QA reported 500s. In the gateway logs some took exactly 9.000 seconds, which is the KrakenD timeout, meaning the backend was hanging. Others failed in 3–6 ms, meaning the backend host didn’t exist. Splitting them that way pointed straight at the dead database and the missing services.

Sign-in broken behind the ingress

Keycloak expected the Forwarded header but ingress-nginx sends X-Forwarded-*, so token issuers came out as http:// and the admin console failed. I switched the proxy-header mode and documented the change until it’s moved into the Helm values.

The cutover, and the way back

  1. Lower DNS TTL 48 hours ahead.
  2. Stop scheduled workers on-premise so no job runs on both sides.
  3. Let sync lag reach zero, then check row counts and checksums.
  4. Switch DNS in the lowest-traffic window and watch closely for 72 hours.
  5. Reverse the sync so on-premise keeps receiving cloud writes.
  6. Keep on-premise warm for one to two weeks, then decommission.

Rollback triggers are written down in advance: error rate and latency thresholds. Because the sync runs in reverse, rolling back means switching DNS back, without losing what users wrote in the meantime.

Still on the list this week

  • End-to-end QA on every user-facing flow against the cloud stack.
  • Tightening the sync to a least-privilege database account.
  • Alarms on sync lag, so a stalled stream pages someone.
  • Moving manual cluster changes back into Helm values and Git.
